# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

## Build & tooling

- `pnpm install` (whose `prepare` script runs `tsdown`, same as `pnpm build`) is the build gate; `npx tsc --noEmit` typechecks without emitting. `pnpm test` runs the vitest suite under `test/`, which `tsconfig.json`'s `include` deliberately excludes so tests never ship in `dist`.
- The package is a dual ESM/CJS unbundled build (`tsdown.config.ts`). Its public surface is exactly `package.json`'s `exports` map (`.`, `./tariff`, `./const`, `./router`, `./types`, `./bluetooth`); deep `dist/...` imports are blocked by design. A new subpath needs an entry in both files. `./tariff` must never pull in `@teslemetry/tesla-protocol` (`@teslemetry/api` inlines it), and `./types` is type-only (`export type *`). CI checks `attw --pack . --profile node16`, runs `test/consumers/` from both module systems, and greps `dist/tariff.*`.
- `tsconfig.json` must keep `"module": "NodeNext"` / `"moduleResolution": "NodeNext"`. `@teslemetry/tesla-protocol` gates its subpaths behind a package.json `exports` map with per-subpath types; under classic/ESNext resolution every scoped-package import (even `@types/node` internals) fails to resolve.
- `__VERSION__` (sent in `X-Library`) is a compile-time `define` from `package.json`, set in **both** `tsdown.config.ts` and `vitest.config.ts`; a new build or test entry point needs it too.
- Tesla protobuf types (`RoutableMessage`, `vcsec`, `car_server`, `signatures`, `keys`, ...) come only from `@teslemetry/tesla-protocol` (subpaths like `@teslemetry/tesla-protocol/command/signatures`); nothing is vendored or generated here. It is ts-proto output: plain-object messages with `Type.create(partial)` / `Type.encode(msg).finish()` / `Type.decode(bytes)`, not `google-protobuf`'s `.setX()`/`.serializeBinary()`.

## Signed commands

- The layer is split as in `python-tesla-fleet-api`: `src/commands.ts` (`Commands`, abstract) builds and HMAC-signs every vehicle command into a `RoutableMessage` and dispatches it through one abstract seam, `_send`; `src/vehiclesigned.ts` (`VehicleSigned`) fills that seam over the cloud `/signed_command` endpoint. Another transport (e.g. BLE) belongs as a second subclass of `Commands`, not as a change to it. `src/signing/` holds the per-domain session state (`session.ts`) and ECDH/SHA-1 key derivation (`crypto.ts`); faults are the Python-named classes in `src/exceptions.ts`, and only `TeslaFleetMessageFaultIncorrectEpoch`/`InvalidTokenOrCounter` drive the bounded epoch-fault retry. `authMethod` picks the signing: `"hmac"` (cloud) sends the command in plaintext, `"aes"` (BLE, as in Python and Tesla's Go SDK) encrypts it and sets `FLAG_ENCRYPT_RESPONSE`.
- Every command a signing-required vehicle would reject on the plaintext endpoint **must** be overridden in `Commands` so it is signed rather than silently inherited unsigned from `VehicleSpecific`. `test/proto-coverage-lock.test.ts` enforces this, and also fails on any `VehicleAction` or `GetVehicleData` field with neither a wrapper nor a reasoned allowlist entry, so a `tesla-protocol` bump must take a decision on each new field. A command on both transports gets a row in `test/cross-transport-parity.test.ts`, which holds the accepted REST/signed gaps with their reasons.
- Trip `order` values are protocol 6's `RemoteNavTripOrderE` (0 replace, 1 prepend, 2 append), not the 1-based values in Python's docstrings, which are on protocol 5. Seat positions differ by command: `Seats` is 0-indexed and only for seat heating; seat cooling and auto seat climate take the 1-indexed `AutoSeat`.
- In `set_scheduled_departure` a present recurrence block is what turns its feature on, so a disabled feature must send no block at all.
- A `SessionInfo` (handshake reply, or piggy-backed on a later reply for resync) is untrusted wire data until `Commands.validate_msg` verifies its `signatureData.sessionInfoTag`: HMAC-SHA256 over the exact received `session_info` bytes, keyed by `HMAC-SHA256(K, "session info")`, TLV-bound to the VIN and to the request's own `uuid` as challenge (`SIGNATURE_TYPE_HMAC` + `TAG_PERSONALIZATION` + `TAG_CHALLENGE`). Only once that tag verifies does `Session.commit` apply the new epoch/counter/clock — and it still refuses a clock that regresses within an epoch and never lets the anti-replay counter roll backward within one. Skipping tag verification, or trusting counter/clock from an unauthenticated reply, is a real vulnerability — don't reintroduce it. Authoritative spec (with the worked vectors `test/hmac-golden-vector.test.ts` reproduces): `pkg/protocol/protocol.md` in `github.com/teslamotors/vehicle-command`, fetchable via `gh api`.
- **The vehicle key is trusted once, at first contact, then pinned, as in Tesla's Go SDK (`Signer.UpdateSignedSessionInfo`). Python's `Commands` still has this flaw.** ECDH is symmetric, so anyone who saw the client's public key can tag a `SessionInfo` naming a key of their own: a tag verified with a key derived from that same reply proves nothing, and adopting the key hands AES-GCM traffic to the attacker. Replies reach key material only through `Session.trustedKeys`, which returns the stored keys once pinned and refuses a different `publicKey`; `commit` keeps the stored keys whatever it is passed. Nothing clears the pin, on reconnect, retry or handshake, so a re-keyed vehicle fails clearly and needs a new instance. `test/helpers/sessionattacker.ts` models this attack; it is kept apart from the honest `FakeVehicle`.
- `validate_msg` takes the request's domain and picks the session by it. A reply's `fromDestination` is unauthenticated, so it is only checked against the request.
- `commit` refuses a clock or counter no command could be signed with, and `Session.nextSignature` guards the same `uint32` limits because the clock keeps running after `commit`. Both raise `SessionInfoAuthenticationFault` and change nothing, rather than reaching ts-proto's bare `invalid uint32`.
- **`resp.requestUuid` must never gate acceptance of a `SessionInfo` reply — only cross-check it when the vehicle actually populated it.** Real VCSEC hardware leaves it empty (protocol.md: "due to memory constraints, the `request_uuid` field is typically not populated in replies from VCSEC"), so an equality-or-reject guard silently breaks every VCSEC command against real vehicles. The `session_info_tag` HMAC, which binds the *sent* uuid as `TAG_CHALLENGE`, is the actual authentication. `test/helpers/fakevehicle.ts` always echoes the uuid and so cannot catch that regression; `FakeVehicle.omitRequestUuidLikeRealVcsec()` reproduces the real-hardware shape.
- For `DOMAIN_VEHICLE_SECURITY`, `Commands.dispatch` holds the domain's session lock across the *entire* dispatch (handshake, build, send, retry), not just message-build: VCSEC requires strict counter order and the spec warns against concurrent requests to it at all. Infotainment (sliding window) keeps the narrower build-only lock.
- `Commands.decryptResponse` runs only when a reply has `AESGCMResponseData`: firmware before 2024.38 ignores the flag and replies in plaintext. Response metadata uses the *response's* flags, always present, and the real request hash length; an HMAC request's hash is 33 bytes to Infotainment, truncated to 17 only for VCSEC. A reply that fails to open says nothing about whether the command ran. `aesGcmDecrypt`'s `authTagLength` is what rejects a truncated tag.
- `_send` must never take `Session.withLock`: `dispatch` holds that non-reentrant lock across `_send` for VCSEC, so it would deadlock every VCSEC command. Nor may `ensureHandshake`, which takes it, run inside it.
- `Commands`'s `#privateKey`/`#publicKey` are native private class fields, not `protected`/TS-only `private` — the raw signing key must be unreachable off the instance entirely (`JSON.stringify`, structured logs), not merely inaccessible to outside code. Tests observe key derivation through a captured handshake message on the wire, never by reading the field.
- `test/helpers/fakevehicle.ts` is a from-scratch reimplementation of the vehicle side (independent HMAC and AES-GCM in both directions, not a mock), so round-trip tests check the client against a second implementation of the wire format.
- `src/signing/jws.ts` (Tesla.SS256) takes the raw key, so a subclass reaches it only through `Commands.signFleetTelemetryConfig`. Its vectors in `test/fixtures/ss256_vectors.json` are Tesla's Go SDK output, copied from Python; never regenerate them. There is deliberately no low-`s` normalisation.

## Bluetooth (`src/bluetooth/`)

- `VehicleBluetooth` is a second subclass of `Commands`, through `BroadcastListeners` (`broadcast.ts`), which stands in for Python's mixin. `./bluetooth` is the only way in: the root entry and `Vehicle` must never load it (`test/bluetooth/entry.test.ts` walks the imports; `test/consumers/cjs.cjs` checks the built result), so `createBluetooth` lives on `VehiclesBluetooth`. It imports no GATT library or native module, and runs on Node `crypto`: a backend arrives as a `BleTransport` (`transport.ts`, whose header holds the adapter rules) that does raw GATT only.
- Homey is the weakest backend and the primary consumer, so the contract asks only for what it does: a fixed 5 s `discover()` with no filter, no connect or write timeout, write-with-response only, no MTU (`maxWriteSize` left out means 20 bytes), and `isConnected` and the disconnect event that can both lie. Every backend call is bounded here, and a read timeout, or a failed write followed by a silent reply window, marks the link lost whatever `isConnected` says. Don't gate link loss on `isConnected` alone, or a dead link wedges behind writes that "succeed" as best-effort.
- An attempt the library gave up on can still land on a backend with no timeout, so `connectOnce` closes it late: the vehicle has three slots. A new connect awaits `teardown`, because a late `disconnect()` on Homey would end the new link to the same peripheral.
- A timed-out mutating command is unresolved, never failed, and is never sent again. Only `BluetoothTransportError` (an adapter's `BleNotSubmittedError`, or nothing written) and `BluetoothCommandFailed` are safe for a router to replay. A mismatching broadcast proves failure only when the whole window ran out, so a lost link that cuts the window short leaves it unconfirmed.
- `UNLOCKED` is the proto3 zero value, so it never appears on the wire and a status with no lock field decodes to it. It proves nothing either way, so no status confirms `door_unlock` (it needs its ack) and none fails `door_lock`. Python compares it and has this flaw, and Node differs on purpose. Only a status received after the write counts.
- Verify plans (`verify.ts`) compare with `sameFloat`: temperatures and volume are float32 on the wire, so a raw `===` against the caller's double reports a command that ran as failed, and a router replays it. A state field the reply left out proves nothing, so it resolves as an unreadable read. Python compares proto defaults there. Never add a plan for a toggle, a relative step or an ack-only action.
- A readiness probe's window opens after the last write, so 20-byte writes cost it nothing; only slow replies need `wake_probe_timeout_ms`. A reply to an earlier probe fails the next one's challenge, so `awaitInfotainment` retries `SessionInfoAuthenticationFault` as it does a timeout. Python would abort the wake there.
- `charge_port_door_open` under `"verify"` is the one mutating path that raises `BluetoothUnconfirmedCommand` with `raise_unconfirmed: false`, and it must keep calling `super.sendVehicleSecurity` to skip the ladder. A read after the opening never fails over, whatever it raises. Node has no cancellation, so preflight's shared deadline is `withTimeout` plus an abort signal that stops the work left behind, and a timed-out VCSEC handshake is ended by dropping the link.
- A reply is checked against its request before anything acts on it (`isForeignReply`), because a late reply to an earlier request can arrive on the same link. Another request's uuid is dropped. An empty uuid is still heard, as real VCSEC leaves it empty, but it can only ack or answer a read: an epoch or WAIT resend, or a fault, needs the echoed uuid or a verified session-info tag. So a real VCSEC WAIT or fault with an empty uuid ends as unconfirmed, not as a resend.
- After a write, the ladders send every failure but the car's own refusal through `leavesOutcomeUnknown`, for all commands. `onSubmitted` tells them a write may have landed, so an argument that fails to encode stays an error and not a best-effort success. The known exception is the resend when VCSEC reports the car asleep, which matches Python and stays.
- `pair` writes through `_send` exactly once and has no retry path to it. It resolves only on an explicit success reply or an authenticated handshake with this key, unlike Python, which takes any reply without a whitelist fault, so a WAIT or a bare ack ends it before the tap. `pairProbe` sends one request rather than call `handshake`, whose auth retry could write after an abort. The late-reply check must run before each probe, because `_send` drains the queue. Holding `Session.withLock` around `_send` there is fine: only `_send` itself must not take it.
- `vehicle_data` with no list or REST endpoint names raises `BluetoothCloudUnavailableError`, so a router sends that call to the cloud. `[]` asks for nothing. Python takes neither: it raises `TypeError` or sends an empty request.
- `test/bluetooth/coverage.test.ts` is the lock on what falls through to REST: a new `VehicleSpecific` method needs a signed override or a reasoned `REST_ONLY` entry.
- `test/helpers/fakeblelink.ts` keeps its own framing, as `FakeVehicle` keeps its own signing, so it must not import `src/bluetooth/framing.ts`. Prove "exactly one" with `FakeBleLink.vcsecWrites`, which holds every VCSEC command the client finished writing, in the clear, even one that never arrived. `FakeVehicle.vcsecCommands`/`infotainmentActions` hold only what arrived, and frame counts include reads.

## Keys (`src/signing/keys.ts`)

- `TeslaFleetApi.get_private_key` returns, and `Commands` takes, a raw 32-byte `Buffer`; `get_rsa_private_key` returns a `KeyObject`, which is what `EnergySpecific` takes. Both live in native `#private` fields behind accessors. The files are PEMs shared with Python (SEC1 and PKCS#1), so don't change the format.
- A raw scalar has no curve, so a non-P-256 EC file is `wrong_type` here, though Python's loader accepts any curve.
- Encrypted-PEM detection reads the PEM markers. OpenSSL's error for a missing passphrase varies across Node versions.
- `test/fixtures/keys.ts` is generated by Python `cryptography`; never regenerate it from Node, or the byte comparisons stop proving anything.

## Energy device commands

- An energy site signs only with the `private_key` passed to it: unlike vehicles, an omitted key means unsigned, nothing reads the parent's `rsa_private_key`, and there is no `false` sentinel. This matches Python's `EnergySite`.
- `EnergySpecific._command` signs everything except `UNSIGNED_DEVICE_COMMANDS`; `TeslemetryEnergySite` overrides every method on `_command` with its own route, and `test/teslemetry-energy.test.ts` fails if one is missed. `src/signing/energy.ts`'s `EnergyDeviceSigner` is stateless RSA, so identical bytes execute again before `expires_at`: a signed send never retries.
- `EnergyDeviceSigner.envelope` takes Python's snake_case names. ts-proto's `fromJSON` reads camelCase and silently drops the rest, so `envelope` converts the keys and `assertParsed` raises on anything dropped, matching Python's `ParseDict`.
- `set_island_mode`, `go_off_grid` and `reconnect_grid` must never reach the unsigned `grpc_command`: gateways acknowledge it without moving the contactor. They go straight to `_signed_command`, never `_command`.
- `src/energyparsers.ts` stays free of protobuf, because Homey calls its free functions on raw `@teslemetry/api` replies. A null body raises `InvalidResponse`; it never means "no clients" or "no address".

## Cloud clients (`src/teslemetry.ts`, `src/tessie.ts`)

- `TeslemetryVehicle` and `TessieVehicle` extend `VehicleSpecific`, and `vehicles.create(vin)` is their only factory. `TeslemetryVehicles`/`TessieVehicles` must still extend `Vehicle`, so the base factories can't be removed: they are shadowed as `undefined as never` fields, which makes calling one a compile error and leaves it undefined at run time. `test/factories.types.ts` enforces that through `npx tsc -p tsconfig.test.json --noEmit`, which CI runs over `test/*.types.ts`; plain `tsc` and vitest never typecheck `test/`.
- Python call sites use keyword arguments, so a Python method with many optional arguments becomes an options object here (with `start`/`end`, sent as `from`/`to`); short ones stay positional, in Python's order. Tessie's `tessie_*` commands take `max_attempts` before `wait_for_completion`, the reverse of every other Tessie command.
- `_request` log lines go through `redactedJson`/`redactedQuery` in `src/log.ts`, matched by key name: `migrate_to_oauth` sends a token in a body, Tessie sends PINs in the query string, and Fleet's `set_pin_to_drive` and `set_valet_mode` call their PIN `password`. A new secret-bearing key belongs in `SECRET_KEYS`. Error lines log a message only for `TeslaFleetError`, whose message is fixed per class; anything else logs its type alone, and error `data` is never logged.

## Router (`src/router/`)

- Port of Python's `router/`; design in Linear document 02. `./router` imports only `exceptions` at run time (`test/router.test.ts` enforces it): a backend that cannot be imported (Bluetooth, Powerwall) marks its own errors with a boolean `failover_safe`. No `Proxy` and no method list: methods come from the backends' prototypes at construction (`methodNames`), and `Routed<B>` types them. The two must agree on what is skipped (`_` names, `then`).
- `BluetoothUnconfirmedCommand` is checked before `on_result` and before the policy, by `instanceof` **and** the `unconfirmed` field. `instanceof` alone fails across the dual-package hazard; `test/consumers/esm.mjs` proves this with both real copies. Unlike Python, `is_failover_safe` itself also answers false for it.
- Backend methods must not use overloads (`infer` reads only the last one). `test/router.types.ts` runs in CI through `tsconfig.test.json`; `test/*.test.ts` is not typechecked at all.

## Observation funnel (`src/funnel.ts`)

A funnel, not a selector: do not add source health, availability, grace windows, priority or per-field selection. Unavailability is a value a source reports, never inferred from a dropped link. The module stays synchronous and never originates a request (`test/funnel.test.ts` checks its syntax tree); polling belongs to the consumer. Translations are positive allowlists: an unmapped value emits nothing.

## Local Powerwall (`src/powerwall/`)

- **Publish gate:** `./powerwall` stays out of `tsdown.config.ts` and `package.json` `exports` until PW-17, after the read-only run on a real gateway. Tests import from `src/`. Write methods have only ever run against `test/helpers/fakegateway.ts`, an independent HTTPS gateway that verifies RSA signatures itself; no autonomous session sends a write to a real one.
- TLS goes through `node:https` with certificate checks off on `V1rTransport`'s own `https.Agent` only: global `fetch` cannot take a self-signed certificate, and `NODE_TLS_REJECT_UNAUTHORIZED` would also disable the cloud's checks. `node:https` decompresses nothing, so every body is gunzipped by magic bytes.
- A v1r POST is sent once, carries no bearer token, and is never retried at any level: the same bytes execute again before `expires_at`. Only REST GETs retry, once, after a 401/403 re-login.
- LAN envelopes are separate from the cloud's: commands set `DELIVERY_CHANNEL_HERMES_COMMAND`, and GraphQL and system-info reads use `LOCAL_HTTPS` with the `INSTALLER` sender. `EnergyDeviceSigner.envelope` is cloud-only and leaves the channel unset.
- `Powerwall*` errors extend `Error`, not `TeslaFleetError`. Only `failover_safe = true` on connection, authentication and rate-limit errors lets a router fail over. A tolerated reply (`cancel_max_backup`, `remove_authorized_client`) swallows only fault and protocol errors, unlike Python, so a dead link never reads as success.
- `PowerwallEnergySite` omits what has no local mapping instead of stubbing it, so a router skips it. `priority` is a decimal string, because `2^64 - 1` does not fit a number.
- Golden envelopes (`test/fixtures/powerwall-envelopes.json`, from the real Python client; never regenerate them here) differ from Node in two expected ways, both asserted in `test/powerwall/golden.test.ts`: `reconnect_grid` omits `force = false`, and a `config.json` write has `JSON.stringify` spacing. `src/powerwall/queries.ts` is pinned by SHA-256: a client cannot sign a new query.
- An empty `MessageEnvelope` encodes to zero bytes, which `post_v1r` rejects, so a fake reply meaning "no response field" must still carry a category, as `{ envelope: { teg: {} } }` does.
- `LiveStatusMerge` and `SiteInfoMerge` own no timer, and `test/powerwall/merge.test.ts` fails if they start one: the caller drives `poll()`. A `SiteInfoMerge` read that a command landed in is discarded by `generation`, because it predates the command's value, but it still updates `healthy`.
- `connect_gateway` persists nothing: `moved` hands the caller a `host` to save. Every outcome returns a client, so a stale one fails over to the cloud rather than breaking the site. Registration and discovery use the cloud backend directly, never the router.
- `scripts/powerwall-readonly-check.ts` runs on a real home's gateway, so it must stay unable to write and must print only key names, types and pass or fail. `test/powerwall/readonly-check.test.ts` checks this on its source, at run time and on the wire, from an allowlist: a new client or site method counts as a write until added to `READS` there, and a new write must join the table in `docs/powerwall.md`. `tsconfig.test.json` also compiles `scripts/*.ts`, so the script's `Pick` types make a write a compile error.

## Errors (`src/exceptions.ts`)

- A class-for-class port of `python-tesla-fleet-api`'s `exceptions.py`: same names, parents, and `message`/`status`/`key`/`code` (as statics, copied onto instances). Add new errors there under their Python name, with no aliases; don't reintroduce per-module error files. `message` is always the class message; per-instance detail goes in `data`.
- `_request` only ever rejects with a `TeslaFleetError` (`MissingToken` for a null token, or via `raise_for_status`, `ResponseError` for a non-JSON success body, or `TeslaFleetConnectionError` with `cause` for fetch/timeout failures) — never a bare object.

## Tariff resolver (`src/tariff.ts`)

`getTariffPeriods(tariff, now, opts)` is a pure Tariff V2 rate resolver mirroring `python-tesla-fleet-api`'s sibling. Invariants worth keeping:

- The tariff carries no timezone; the caller must pass `opts.timeZone` (IANA, e.g. `site_info.installation_time_zone`) — there is no other way to get site-local wall-clock parts from a JS `Date`.
- Resolution is one calendar day at a time (`dayPeriods`), not a minute-of-week span: a `tou_periods` entry's `fromDayOfWeek..toDayOfWeek` means "this daily window recurs on these weekdays". `nextChange`/`upcoming` re-resolve the season per day so a horizon crossing a season boundary re-prices, and a gap between periods is reported as a gap.
- Wall-clock boundary → `Date` goes through `wallClockToUtcMillis` (iterative: the zone's offset at the target instant is what's being solved for), never by adding elapsed minutes to `now`. The reverse — "what calendar day is N wall-clock minutes from now" — must go through `wallClockAt` (pure calendar arithmetic), never `now.getTime() + minutes*60000`, which lands on the wrong day across a DST fall-back (25h) or spring-forward (23h) day.
- Buy and sell resolve independently via `scheduleAt`, which reports `nextChangeGM`/`sinceGM` even for a grid sitting in a gap (a sell window not yet open, or closed). `nextChange` (earlier of the two) and `currentStart` (later) must fold in the sell side even when sell has no active period, or a differently-scheduled sell tariff is silently ignored or backdated. Both are nullable (bounded to one day of lookahead/lookback) and must be excluded via `!= null`, never treated as `0`.
- `TariffContentV2.seasons` (`src/types/site_info.ts`) is `Record<string, Season>` — an object keyed by season name, not an array. Don't regress it to an array shape.

## Releases

Releases go through Changesets, not hand-cut GitHub Releases: a PR that changes behavior includes a changeset (`pnpm changeset`). Merging to `main` runs `.github/workflows/publish.yml`, whose `validate` job re-runs `reusable-ci.yml` (lint/typecheck/test/publint/pack) on the exact SHA being released and whose `release` job (`needs: validate`) either opens/updates a "Version Packages" PR or, if one was just merged, publishes via `changeset publish`.

- `ci.yml` and `publish.yml`'s `validate` both call `reusable-ci.yml` — keep checks there, not duplicated inline, and keep `needs: validate` so a stale CI run on another SHA can never stand in for the one being published.
- `reusable-ci.yml`'s `gate` job exists to keep the check name `Build, Lint & Test / Build, Lint & Test`, which the `main` ruleset requires; the Node matrix job would otherwise report one differently named check per version.
- The `production` environment has no protection rules configured: merging the "Version Packages" PR is the sole approval gate, and `release` publishes immediately after.
- Publishing uses npm trusted publishing (OIDC, `id-token: write`, no `NPM_TOKEN`). It must be configured per-package on npmjs.com (package Settings → Trusted Publisher, github-actions provider, matching repo + `.github/workflows/publish.yml`).
- `--provenance` requires `package.json`'s `repository.url` to resolve to `https://github.com/Teslemetry/node-tesla-fleet-api`; sigstore checks it against the Actions run's own repo and fails the publish (`E422`) on a mismatch.
- Before assuming a version is live, check `npm view tesla-fleet-api@<version>` rather than trusting `package.json`.
